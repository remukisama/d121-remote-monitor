# 软件设计与验证说明

本页对应仓库中的两从站配置，介绍 RT-Thread 在项目中的实际使用，以及关键事件补传的验收范围。源码和历史记录可通过文内链接查看；图像和测试结果均为对应时点的记录。

## 数据流

```text
星火：温湿度、六轴 ─┐
                   ├─ RS485 / Modbus RTU ─ D12X：采集、显示、TF 记录与回放
龙芯：系统指标 ─────┘                            │
                                                ├─ 关键事件与可用事前摘要 → NOR 队列
                                                └─ ESP8266 / MQTT → 云后台 → 微信小程序
                                                                  └─ 保存确认 → D12X 出队
```

星火从站与 D12X 主站运行 RT-Thread；龙芯从站运行 LoongOS。当前代码与界面针对地址 1 和 2 设计，接入更多从站需扩展并重新验证。目标记录速率为星火约 10 Hz、龙芯约 1 Hz，不等于任何情况下都保证达到该速率。

## RT-Thread 线程与组件

| 运行位置 | 线程或机制 | 作用与源码 |
|---|---|---|
| D12X | `bb` 采集线程，优先级 19 | 轮询星火、判定事件、写入记录，并调用龙芯数据采集步骤；见 [bb.c](../firmware/d121/overlay/application/rt-thread/helloworld/blackbox/bb.c) |
| D12X | `cloud` 网络线程，优先级 24 | 管理 ESP8266 串口、连接和本地事件队列；见 [cloud.c](../firmware/d121/overlay/application/rt-thread/helloworld/cloud/cloud.c) |
| D12X | `mon_ctl` 和 `bb_hist` 工作线程 | 分别处理采集启停及历史读取；由界面按操作创建，避免把文件访问直接放在触摸回调里；见 [monitor_ui.c](../firmware/d121/overlay/packages/artinchip/lvgl-ui/aic_demo/demo_hub/app/monitor/monitor_ui.c) |
| D12X | LVGL 定时器 | 页面使用 250 ms 定时器刷新；这是界面刷新周期，不是采样周期或端到端延迟保证；见 [monitor_ui.c](../firmware/d121/overlay/packages/artinchip/lvgl-ui/aic_demo/demo_hub/app/monitor/monitor_ui.c) |
| D12X | 信号量、互斥量与设备框架 | RS485 接收回调释放信号量；总线互斥量保护半双工请求与应答；通过设备框架打开串口；见 [rs485_master.c](../firmware/d121/overlay/application/rt-thread/helloworld/rs485/rs485_master.c) |
| D12X | DFS 文件接口 | TF 用于采集记录与历史读取，NOR 数据区用于关键事件队列；见 [bb_store.c](../firmware/d121/overlay/application/rt-thread/helloworld/blackbox/bb_store.c) 和 [cloud_outbox.c](../firmware/d121/overlay/application/rt-thread/helloworld/cloud/cloud_outbox.c) |
| 星火 | `sparkimu`、`sparkenv`、`rs485_s` | 分别执行 IMU 采样、环境采样和从站应答；传感器缓存及锁见 [spark_imu.c](../firmware/star-stm32f407/applications/spark_imu.c)，协议线程见 [rs485_app.c](../firmware/star-stm32f407/applications/rs485_app.c) |
| 星火 | 信号量和互斥量 | 用于 RS485 接收通知及发送保护；见 [rs485_drv.c](../firmware/star-stm32f407/applications/rs485_drv.c) |

上表是源码中的设计和参数，不是实时调度测量。RT-Thread 优先级数字越小表示优先级越高；运行时仍受 I/O、超时和其他任务影响。

## 关键事件怎样补传

1. 主站识别到需要上传的关键事件后，网络线程将事件及可用的事前有效摘要写入 NOR 队列。
2. 网络恢复后，设备通过 MQTT QoS 0 逐部分发送；云后台完成数据库提交后发送应用层确认。
3. 设备收到相关确认后移除队首；确认超时会重试，后台依据事件身份去重。

这是应用层补传机制，不应描述成 MQTT QoS 1。队列容量有限；普通实时摘要和完整 TF 原始波形不在全部补传的范围内。事件若尚未进入持久队列、队列已满或存储介质故障，不能承诺零丢失。实现和具体边界见[关键事件可靠补传](../可靠补传说明.md)。

## 已记录的验证

| 场景 | 结果 | 说明 |
|---|---|---|
| 独立 Modbus 工具 | 每站交替读取 20 次；还检查了星火 LED 读写和异常响应 | 经过 D12X UART 桥转发至真实总线；见 [Modbus 记录](evidence/modbus-acceptance.md) |
| 短时网络及单站故障 | 2026-10-25 暂停网络 20 秒并停止/恢复星火接收；龙芯继续采集，队列 2 → 0，应用确认计数 16 → 24 | 这是一次受控短时测试，确认计数不等于唯一事件数；见[故障结果](evidence/short-fault-result.json)和[网络记录](evidence/network-acceptance.md) |
| 设备 TLS | 正确 CA/域名连接，以及错误 CA、错误域名和过期证书拒绝对照通过 | 测试的是设备到 MQTT 服务的链路；后台接收侧的 MQTT 配置未在该轮改为 TLS；见[网络记录](evidence/network-acceptance.md) |
| 云端与手机 | 微信云端 15 项复验通过；手机移动网络的登录、双站实时数据、历史列表和事件详情四项由用户确认正常 | 手机验收为用户反馈，并非独立抓包或公众版发布审核；见[手机验收](evidence/mobile-network-acceptance.json) |
| 数据库恢复 | 2026-10-22 将生产 MySQL 一致性备份恢复至隔离新库，七表摘要及业务查询比较通过 | 不等于生产库替换或平台整集群回档；见[数据库恢复](evidence/database-recovery.md) |
| 自动检查 | 后端、客户端与部分固件主机测试由 GitHub Actions 执行 | [工作流](../.github/workflows/ci.yml)和[运行记录](https://github.com/remukisama/d121-remote-monitor/actions)；不能替代真实设备联调 |

长期观测按既有安排暂停；更多从站、任意时刻断电零损失、微信公众版审核均未验收。龙芯普通系统软件重启存在已记录问题，见[龙芯从站说明](../firmware/loongson-slave2/README.md)。
